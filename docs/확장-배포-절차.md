# Chrome 웹스토어 배포 절차 — 반드시 이 순서대로

> **왜 이 문서가 필요한가**: 2.1.0 버전을 웹스토어에 올릴 때, 정식 빌드 산출물이 아니라
> 로컬에 남아있던 `viewlens-v2.1.0.zip`(개발용 `SERVER_URL=http://localhost:3000`이 그대로
> 든 파일)이 실수로 업로드된 적이 있다. 이 버전을 설치한 참여자는 시청 데이터가 서버로 **전혀
> 전송되지 않았다**(확장 코드가 오류를 조용히 삼켜서 참여자 화면엔 아무 이상도 안 보임).
> 이 문서는 같은 사고를 막기 위한 절차다.

---

## 핵심 규칙

**Chrome 웹스토어에는 GitHub Release에서 다운로드한 zip만 올린다. 로컬에서 만든 zip은 절대 올리지 않는다.**

로컬 zip(`viewlens-*.zip`)은 개발 중 수동 테스트용으로만 쓴다 — `.gitignore`에 걸려 있어 커밋되지
않고, `SERVER_URL`이 로컬 개발값(`http://localhost:3000`)으로 잘못 들어가 있을 위험이 항상 있다.
반면 GitHub Release 산출물은 `.github/workflows/release-extension.yml`이 **GitHub Secrets에서
`SERVER_URL`을 읽어 자동으로 `config.js`를 생성**하므로 안전하다.
(`GEMINI_API_KEY`/`YOUTUBE_API_KEY`는 더 이상 확장 프로그램에 들어가지 않는다 — "오늘 리뷰"
생성과 YouTube categoryId 조회를 모두 서버로 옮기면서 제거했다. 확장 프로그램 파일을
열어보면 키가 그대로 노출되는 문제가 있었다.)

---

## 연구 기간 중 배포 규칙

**첫 참여자가 설치한 날부터 마지막 참여자의 전송 기한이 끝날 때까지는 확장을 배포하지 않는다.**

- 연구 중간에 확장이 바뀌면 기간마다 수집 방식이 달라진다. 업데이트가 참여자마다 다른 시각에
  들어가서 어느 기록부터 바뀌었는지도 가르기 어렵다.
- 예외는 **수집이나 전송이 깨져 데이터가 계속 사라지는 버그**뿐이다. 화면 문구, 표시 오류처럼
  데이터에 영향이 없는 수정은 연구가 끝난 뒤에 배포한다.
- 연구 전 마지막 릴리스를 낸 뒤에는 확장 코드를 동결한다.

### 긴급 배포가 필요할 때

1. **참여자에게 재설치를 요청하지 않는다.** 확장을 제거하면 로컬 저장소가 통째로 지워져,
   아직 서버에 보내지 못한 영상 기록·세션·시청 시간이 함께 사라진다. 다시 설치한 뒤에도
   참여자 코드를 다시 입력해야 한다.
2. **자동 업데이트를 기다린다.** 공개 상태(공개·미등록·비공개)와 관계없이, Chrome이 몇 시간마다
   새 버전을 확인해 스스로 설치한다. 참여자가 할 일은 없다. 심사가 끝나 대시보드 상태가
   "게시됨"이 된 뒤부터 시간을 센다.
3. **새 권한을 추가하지 않는다.** 경고가 뜨는 권한이 추가되면 Chrome이 확장을 비활성화하고
   참여자의 승인을 기다린다. 그동안 수집이 멈춘다.
4. **열린 유튜브 탭은 따로 안내하지 않는다.** 업데이트되면 background가 열린 유튜브 탭에 수집
   스크립트를 다시 넣어 새로고침하지 않아도 기록이 이어진다(`background.js`의 `onInstalled`).
5. 연구자 기기에서 업데이트가 들어오는지 확인한다. `chrome://extensions`에서 오른쪽 위
   **개발자 모드**를 켜고 왼쪽 위 **업데이트** 버튼을 누르면 바로 확인한다. ViewLens 카드의
   버전이 새 번호로 바뀌면 된다. 이 버튼은 개발자 모드가 필요하므로 참여자에게는 안내하지 않는다.

### 업데이트 뒤 열린 탭 수집 확인(재주입)

배포 전에 압축해제 버전으로 확인한다. 연구 데이터와 섞이지 않게 테스트용 Chrome 프로필에서 한다.

1. 유튜브 탭을 새로고침한 뒤 영상을 20초 이상 재생한다.
2. `chrome://extensions`의 ViewLens 카드에서 **↻(새로고침)** 을 누른다. 업데이트와 같은 상황이다.
3. 유튜브 탭을 새로고침하지 않고 다른 영상으로 옮긴다.
4. 탭 콘솔(F12 → Console)에 `[content] recorded:`가 새 영상으로 나오고, 빨간 오류
   (`Identifier '...' has already been declared` 등)가 없어야 한다. 끊긴 옛 스크립트의
   "확장 컨텍스트 무효화됨" 경고는 함께 떠도 정상이다.
5. 서비스 워커 콘솔(ViewLens 카드의 "서비스 워커" 링크)에서 저장된 기록을 확인한다.
   마지막 기록이 새 영상이고, 1번에서 재생하던 영상이 두 번 기록되지 않아야 한다.

   ```js
   const all = await chrome.storage.local.get(null);
   ({
     lastRecordedVideo: all.lastRecordedVideo,
     videoKeys: Object.keys(all).filter((k) => k.startsWith("video__")),
   });
   ```

세션은 마지막 영상 뒤 10분이 지나면 닫혀 `video__` 기록이 `sessions`로 옮겨가므로, 10분 안에 끝낸다.

## 배포 절차

### 1. GitHub Release 초안 생성 확인

`main` 브랜치에 `extension/` 변경이 포함된 PR이 머지되면 Release Drafter → `release-extension.yml`이
자동으로 실행되어, GitHub Releases 페이지에 **초안(Draft) 릴리스**가 만들어지고 그 안에
`youtube-bias-feedback.zip`이 첨부된다.

- 저장소의 **Releases** 탭에서 가장 최근 Draft를 연다.
- 첨부파일 `youtube-bias-feedback.zip`을 **여기서만** 다운로드한다. 로컬 디스크에 있는
  `viewlens-*.zip`은 절대 쓰지 않는다.

### 2. 업로드 전 반드시 zip 내용 확인 (사고 재발 방지의 핵심)

확장 프로그램에는 더 이상 API 키가 없으므로(YouTube categoryId 조회·Gemini 리뷰 생성
모두 서버가 처리), `SERVER_URL`만 값 그대로 확인하면 된다.

```bash
CONFIG=$(mktemp)
trap 'rm -f "$CONFIG"' EXIT

if ! unzip -p youtube-bias-feedback.zip config.js > "$CONFIG" || [ ! -s "$CONFIG" ]; then
  echo "❌ config.js를 추출하지 못했습니다 — zip 파일을 다시 확인하세요"
  exit 1
fi

grep -E 'SERVER_URL' "$CONFIG"
```

`trap ... EXIT`를 걸어둬서 검증 중간에 오류가 나거나 스크립트가 중단돼도 임시 파일이
남지 않는다(정상 종료 시의 `rm`만 믿지 않는다).

다음이 맞는지 확인:

- `SERVER_URL`이 정확히 `https://viewlens.site` (`http://localhost` 아님, 오타 없음)

다르면 **업로드하지 말고**, GitHub Secrets(`SERVER_URL`) 설정이나 워크플로 실행 로그부터 확인한다.

### 3. Chrome 웹스토어 개발자 대시보드에 업로드

1. https://chrome.google.com/webstore/devconsole 접속
2. ViewLens 항목 선택 → 새 버전 업로드
3. 2번에서 검증한 **그 zip 파일 그대로** 업로드 (재압축 금지 — 압축 해제 후 다시 zip으로 묶으면
   파일 구조가 달라질 수 있음)
4. 버전 번호가 `manifest.json`과 일치하는지 확인 후 게시 심사 제출

### 4. 게시 후 실제로 검증 (반드시 스킵하지 말 것)

게시(또는 테스터 채널 반영) 후, **웹스토어에서 직접 설치**해서 확인한다 — 로컬 압축해제 버전이
아니라 실제로 스토어에서 받은 것으로 확인해야 의미가 있다.

1. `chrome://extensions`에서 방금 설치한 ViewLens 카드의 **"세부정보"** → **"출처"**가
   **"Chrome 웹 스토어"**로 나오는지 확인 (여기서 "압축해제된 확장 프로그램"이 나오면 잘못
   설치한 것 — 이전에 로드해둔 로컬 버전을 보고 있는 것일 수 있다)
2. 유튜브에서 영상 하나 재생
3. `pm2 logs youtube-bias-server`(운영 서버 SSH) 또는 서버의 `/health`가 아니라, 실제로
   `video_events`에 방금 그 영상이 기록됐는지 DB로 직접 확인:
   ```bash
   cd ~/youtube-bias-feedback/server
   set -a; . .env; set +a
   node -e "
   const Database = require('better-sqlite3-multiple-ciphers');
   const db = new Database('youtube_bias.db');
   db.pragma(\"cipher = 'sqlcipher'\");
   db.key(Buffer.from(process.env.DB_ENCRYPTION_KEY));
   console.log(db.prepare('SELECT * FROM video_events ORDER BY id DESC LIMIT 3').all());
   "
   ```
   방금 재생한 영상이 여기 나와야 진짜로 검증된 것이다.

이 4번 단계를 생략하면, config.js 내용이 맞아 보여도(3번까지) 실제로 참여자 손에 들어갔을 때
동작하는지는 확인되지 않는다 — 2.1.0 사고도 "빌드는 했지만 실제로 설치해서 테스트하지 않은"
것이 마지막 방어선이 없었던 이유다.

## 로컬 zip 파일 관리

- `viewlens-*.zip`처럼 로컬에서 만든 zip은 테스트 후 바로 삭제하거나, 최소한 파일명에
  `-local-test`처럼 구분되게 표시해서 정식 릴리스 zip과 섞이지 않게 한다.
- 저장소 루트에 여러 버전의 zip이 쌓여 있으면(`viewlens-v1.0.0.zip`, `viewlens-v2.1.0.zip` 등)
  이번처럼 헷갈려서 잘못된 걸 올릴 위험이 커진다 — 정기적으로 정리한다.

## 체크리스트 (배포할 때마다)

- [ ] 연구 기간이 아닌지 확인 (연구 기간이면 데이터가 사라지는 버그의 긴급 수정인지 확인)
- [ ] `manifest.json`의 `permissions`·`host_permissions`가 지난 릴리스와 같은지 확인
      (연구 기간에는 바꾸지 않는다)
- [ ] 권한이 바뀐 릴리스는 웹스토어 업데이트 뒤 권한 경고·비활성화가 없는지 연구자 기기에서 확인
      (`scripting`을 처음 넣는 연구 전 마지막 릴리스 포함)
- [ ] 압축해제 버전으로 "업데이트 뒤 열린 탭 수집 확인" 통과
- [ ] GitHub Releases 페이지에서 zip 다운로드 (로컬 zip 아님)
- [ ] `unzip -p ... config.js`로 `SERVER_URL=https://viewlens.site` 확인
      (`GEMINI_API_KEY`/`YOUTUBE_API_KEY`는 더 이상 확장에 없다)
- [ ] 웹스토어에 업로드
- [ ] 게시 후 실제 설치해서 "출처: Chrome 웹 스토어" 확인
- [ ] 영상 재생 → DB에 실제로 기록되는지 확인
