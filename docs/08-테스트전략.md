# 테스트 현황 진단 및 전략 (2차 테스트 이전)

작성 기준: `develop` 브랜치, 코드베이스 직접 분석(가정 없이 실제 소스·테스트 파일 대조).
"확인 필요"로 표기한 항목 외에는 모두 실제 코드를 읽고 검증한 사실이다.

---

## 0. 결론 먼저

- 기존 테스트(16개 파일, vitest)는 **품질이 낮지 않다.** 특히 `analysis.js`, `llm.js`, `baseline.js`, `study-period.js`, `period-reviews-query.js`, `period-boundaries.js`, `rateLimiter.js`는 경계값·실패 분기까지 촘촘히 짜여 있다. "테스트를 처음부터 새로 깔아야 하는" 상태가 아니라 **"검증된 패턴을 커버리지 사각지대에 그대로 복제 적용하면 되는"** 상태다.
- 진짜 위험은 두 가지로 좁혀진다.
  1. **서버의 1차 데이터 수집 엔드포인트(`routes/sessions.js`, `routes/participants.js`)가 라우트 레벨에서 전혀 테스트되지 않았다.** 연구 데이터 무결성과 직결된다.
  2. **핵심 계산 로직이 3곳에 중복 구현되어 있는데, 그중 팝업 UI 쪽 사본만 테스트가 없다.** 실제로 이 패턴(상수/로직 중복 drift)이 이미 두 번 실버그를 냈다(`viewlens-data.js`의 TIMELINE 하드코딩, `period-reviews-query.js`의 range 체크 누락 — 둘 다 코드 주석에 "coderabbitai 리뷰로 발견"이라고 적혀 있음). 다음 번 같은 종류의 버그가 숨을 자리는 `viewlens-popup.js`의 `mergeDist`다.

### 1.3 Happy path 편중 구간

- `server/routes/period-reviews.js`, `today-reviews.js`: 라우트 자체(파라미터 파싱, `success`/`fail` 응답 포맷)는 성공 경로만 우회 검증되고, 잘못된 쿼리스트링·본문 형태에 대한 라우트 레벨 테스트가 없다(내부 로직은 잘 테스트됨 — 라우트 wiring만 공백).
- `study-end-code.js` 라우트: rate limiter 연결과 `verifyAndRecordStudyEndCode` 호출이라는 "배선"이 실제로 맞물려 동작하는지는 미검증(내부 함수만 단위 테스트됨).

### 1.4 중복/의미 약한 테스트

중복 테스트는 거의 없다. 다만 **"검증이 필요한 지점에 검증이 없는" 구조적 중복**이 있다 — 아래 표.

| 로직 | 위치 A(테스트됨) | 위치 B(미테스트) | 위험 |
|---|---|---|---|
| `isBaselinePeriod` | `extension/pipeline/baseline.js` | `extension/popup/viewlens-data.js` (동일 로직 재정의, 모듈 경계 때문에 중복) | 값이 갈라져도 아무 테스트도 실패하지 않음 |
| `isConGroup` | `extension/pipeline/study-period.js` | `extension/popup/viewlens-data.js` | 상동 |
| `isTestGroup` | 없음(background.js에서 처음 정의) | `background.js`와 `viewlens-data.js`에 각각 독립 정의, 어느 쪽도 서로 대조되지 않음 | 두 사본이 이미 다른 코드베이스 시점 기준으로 작성되어 drift 가능 |
| 카테고리 분포 가중 병합 | `extension/pipeline/analysis.js`(`mergeCategoryDistribution`, 간접 테스트됨) / `server/pipeline/period-boundaries.js`(`mergeSessionDistributions`, 직접 테스트됨) | `extension/popup/viewlens-popup.js`(`mergeDist`) | 코드 주석에 "server의 mergeSessionDistributions와 동일한 가중 병합이어야 한다"고 명시돼 있음에도 동치성 테스트가 전혀 없음. **가장 우선순위 높은 회귀 위험** |

기존 테스트 중 삭제/통합이 필요한 "의미가 약한" 테스트는 발견되지 않았다 — 있는 테스트는 다 제 몫을 하고 있다.

### 1.5 단위/엣지케이스/통합 중 부족한 영역

- **단위 테스트**: 확장 쪽 순수 함수 다수(`content.js`, `youtube.js`, `viewlens-popup.js`), 서버 라우트 검증 함수(`sessions.js`의 `validateSession`, `popup-events.js`/`video-events.js`의 검증 함수)가 완전 공백.
- **엣지케이스**: 존재하는 테스트들의 경계값 커버리지는 좋은 편이나, "여러 탭 동시 시청", "서버 다운 중 데이터 유실", "DB 마이그레이션 재실행" 같은 **인프라/동시성 엣지케이스**는 단위 테스트 스타일로 접근하기 어려워 아예 다뤄지지 않고 있다(뒤에서 별도 절로 다룸).
- **통합 테스트**: 현재 `server/test/routes/*`는 라우트 함수가 아니라 그 안에서 분리해낸 순수 로직만 부르는 방식이라, **실제 HTTP 요청→Express 라우터→미들웨어→DB**로 이어지는 흐름을 검증하는 진짜 통합 테스트는 0건이다(`supertest` 등 미사용, `package.json`에도 없음). `app.js` 자체를 부팅해서 확인하는 테스트도 없다.

## 4. 단위 테스트 후보 상세 (A)

### 4.1 `server/routes/sessions.js` — `validateSession`
- **왜**: 세션 하나가 곧 연구 데이터 1행. 잘못된 값이 그대로 DB에 쌓이면 통계 분석 단계에서야 발견되고, 그때는 되돌릴 수 없다.
- **입력**: `{anonymousId, sessionId, startTime, endTime, videoCount, entropy, llmStatus, failureReason, httpStatus, timedOut, review, reviewTopic, source, promptVersion}`
- 정상: 필수 필드만 있는 최소 payload / 모든 옵션 필드까지 채운 payload
- 경계값: `videoCount = 0`(허용), `videoCount = -1`(거부), `entropy = 0`(허용), `entropy = -0.01`(거부), `timedOut`이 `0`/`1` 외의 값(예: `true`, `2`)
- 잘못된 입력: `startTime`/`endTime`이 파싱 불가 문자열, `body`가 배열이거나 `null`
- 예상 못한 입력: `llmStatus`/`failureReason`/`source`가 목록에 없는 새 문자열(확장 쪽 버전 업그레이드로 새 값이 먼저 배포된 경우), `review`가 빈 문자열(`""`)인데 `undefined`/`null`은 아닌 경우
- 예외 상황: `sessionId` UNIQUE 충돌 → 409 `DUPLICATE_SESSION`으로 응답하는지

### 4.2 `server/routes/participants.js` — 등록 라우트
- **왜**: 그룹 배정(EXP/CON) 오류는 실험 타당성 자체를 훼손한다. 여기서 나는 버그는 재현·수정이 불가능하다(이미 배정된 참여자를 되돌릴 수 없음).
- 정상: 발급 코드 목록이 비어있을 때(시드 전) permissive 등록 / 발급된 코드로 정상 등록
- 경계값: `issued_codes` 개수가 정확히 1개일 때 코드 검증 활성화 전환
- 잘못된 입력: TEST 코드가 아닌데 발급 목록에 없는 코드, `installDate`가 미래 날짜(현재 코드는 이를 막지 않음 — 검증 필요)
- 예상 못한 입력: 동시에 같은 `anonymousId`로 두 번 POST(경쟁 조건) → 두 번째 요청이 `SQLITE_CONSTRAINT_UNIQUE`를 성공 응답으로 흡수하는지
- 예외 상황: `group_code`가 issued_codes의 값으로 덮어써지는 분기(클라이언트가 보낸 group_code와 실제 저장되는 값이 다를 수 있음 — 이 자체가 테스트로 문서화돼야 할 동작)

### 4.3 `extension/content.js` — `extractVideoId`, `parseTitle`
- **왜**: 이 값이 틀리면 이후 파이프라인 전체가 엉뚱한 영상을 기록한다. 순수 함수라 비용 대비 효과가 가장 높다.
- `extractVideoId`: `/watch?v=X` 정상, `/shorts/X` 정상, `/shorts/`(id 없음) → null, `/playlist?list=...` → null, 잘못된 URL 문자열 → null(throw 안 됨), `v` 파라미터 없는 `/watch` → null
- `parseTitle`: `"(3) 영상 제목 - YouTube"` → `"영상 제목"`, `document.title`이 정확히 `"YouTube"` → null, 접두사만 있고 접미사 없는 경우, 빈 문자열 → null

### 4.4 `extension/pipeline/youtube.js` — `fetchVideoCategories`
- **왜**: YouTube API는 외부 의존성이라 실패 모드가 다양하고, 실패해도 분석 파이프라인이 죽지 않게(null로 폴백) 만든 방어 로직이 핵심이라 반드시 회귀 보호가 필요하다.
- 정상: 50개 이하 단일 배치
- 경계값: 정확히 50개(배치 경계), 51개(2배치로 분할되는지)
- 잘못된 입력: 빈 배열
- 예상 못한 입력: API가 요청한 일부 id에 대해서만 `items`를 반환(삭제/비공개 영상 섞임) → 응답에 없는 id는 null로 유지되는지
- 예외 상황: `response.ok === false`, `fetch` 자체가 reject

### 4.5 `extension/popup/viewlens-popup.js` — `mergeDist`, `buildWeeksData`, `calculateBaselineEntropy`
- **왜**: 팝업이 사용자에게 보여주는 최종 숫자. 서버(`mergeSessionDistributions`)와 반드시 같은 결과를 내야 하는데 현재는 그 보장이 코드 주석뿐이다.
- 서버 로직과 동일 입력에 대해 동일 출력을 내는지 대조 테스트(동치성)
- 경계값: 세션 0개, 세션 1개, `videoCount` 미지정(폴백)
- `calculateBaselineEntropy`: 베이스라인 주차가 0개일 때(나눗셈 0/0) 동작 확인 필요

### 4.6 `server/db.js` — `addColumn`
- **왜**: 실제로 프로덕션에서 "no column named X" 에러를 낸 이력이 코드 주석에 명시돼 있다. 회귀가 나면 서버 기동 자체가 실패한다.
- 정상: 컬럼이 없는 테이블에 처음 추가
- 경계값: 이미 컬럼이 있는 테이블에 다시 실행(멱등성)
- 예외 상황: 컬럼 추가가 아닌 다른 이유로 실패하면(예: 테이블 자체가 없음) 에러가 그대로 전파되는지(삼켜지면 안 됨)

| 엣지 케이스 | 현재 코드 상태 (확인됨) | 필요한 조치 |
|---|---|---|
| **여러 탭에서 동시 시청** | `content.js`/`storage.js` 모두 `chrome.storage.local`의 전역 키 `currentSession` 하나만 사용. 탭/윈도우 구분 없음 → 두 탭에서 다른 영상을 보면 하나의 세션 객체에 섞여 기록됨(사양이 아니라 **미해결 상태로 확인됨**) | 테스트로 "현재 동작"을 먼저 고정한 뒤, 의도된 동작인지 사용자(연구자)가 결정 필요 |
| **서버 장애 중 데이터 유실** | `postSessionToServer`/`postTodayCumulativeReviewToServer`는 실패 시 `console.warn`만 하고 재시도·큐잉 없음(코드로 확인됨, `docs/blog/2차테스트이전작업.md`에도 미해결로 기록됨) | 로컬 재시도 큐 구현 전, 최소한 "실패 시 유실됨"을 검증하는 테스트로 현재 리스크를 문서화 |
| **동일 영상 재시청(중복 방지)** | `session.videos.at(-1)?.videoId === videoId`면 무시 — **바로 직전 항목과만 비교**, 그 이전에 봤던 영상으로 되돌아가면 중복으로 다시 기록됨 | 단위 테스트로 "바로 직전과만 비교"가 의도된 동작인지 명시 |
| **데이터 없음(0개 세션)** | `aggregateTodayCumulative([])` → `null` (테스트됨) / `aggregateDailyData([])` → 7일 전부 null (테스트됨) | 이미 커버됨 — 참고용으로 매트릭스에만 기재 |
| **세션 1개뿐** | `calculateEntropy({단일카테고리:1})` → 0 (테스트됨) | 커버됨 |
| **데이터 매우 많음(대량 세션/영상)** | `aggregateDailyData`, `mergeSessionDistributions` 등에 상한 없음 — 성능 테스트 없음 | 벤치마크성 테스트 1개 정도(수백~수천 세션) 권장, P2 |
| **null/undefined/빈 문자열** | 서버 검증 함수들은 대체로 잘 처리(직접 확인) — 단, `sessions.js`의 `feedbackNotifiedAt`처럼 "보내면 검증, 안 보내면 통과"인 필드가 많아 **하위호환 허용 범위**가 테스트로 문서화되어 있지 않음 | 필드별로 "미전송 허용 vs 빈 문자열 거부"를 표로 만들고 테스트로 고정 |
| **잘못된 형식의 데이터(외부 API 응답)** | `youtube.js`가 `item.snippet?.categoryId ?? null`로 방어 중이나, `categoryId`가 숫자가 아닌 문자열로 와도(API 스펙상 항상 문자열) 그대로 통과 — `categories.js`의 `getCategoryName`이 `String(categoryId)`로 재변환하므로 타입 불일치는 실질적 위험 낮음 | 낮은 우선순위, 회귀 방지용 스냅샷 테스트 정도 |
| **중복 데이터(참여코드 중복 등록)** | `check-duplicate-participants.js`가 이미 이 문제를 배포 전 점검용으로 다루고 있음(테스트만 없음) | 4.6절 후보에 포함, P2 |
| **시간대 경계(자정 전후)** | `analysis.js`/`period-boundaries.js` 모두 `toLocaleDateString("sv")` 로컬 vs KST 기준을 각각 다르게 사용 — **확장은 로컬 시간대, 서버는 KST 고정**. 참여자가 해외에서 접속하면 "오늘"의 기준이 서버와 클라이언트에서 어긋날 수 있음(확인됨, 실제 영향 범위는 "확인 필요" — 연구 대상이 전원 국내인지에 따라 리스크 크기가 달라짐) | 시간대 불일치 시나리오를 명시적 테스트로 고정, 연구 설계상 문제 없는지 확인 필요 |
| **동시 요청(rate limit 경합)** | `rateLimiter.js`는 단일 프로세스 인메모리 `Map` — 서버가 멀티 프로세스/재시작되면 카운트가 초기화됨(단일 인스턴스 운영이면 문제 없음, **확인 필요**: 배포 구성이 단일 프로세스인지) | 배포 구성 확인 후 필요 시에만 대응 |
| **네트워크 오류(Gemini/YouTube API)** | `llm.js`/`youtube.js` 모두 폴백 경로 있음(테스트됨/미테스트) | `youtube.js`만 4.4절로 보완 필요 |
| **예상 못한 외부 데이터 구조(Gemini 응답)** | `llm.js`가 `topic`/`feedback` 타입·공백까지 방어(테스트 우수) | 이미 잘 커버됨 |

## 6. 통합 테스트가 필요한 핵심 사용자 흐름 (C)

우선순위(장애 가능성 × 사용자 영향 × 데이터 손실 위험 × 기존 커버리지 부족)로 정렬.

### 6.1 [P0] 시청 감지 → 세션 종료 → 분석 → 피드백 생성 → 서버 저장
`content.js`(감지) → `storage.js`(누적) → `background.js: checkSessionTimeout/analyzeSession`(종료 판정) → `youtube.js`(카테고리 조회) → `analysis.js`(집계) → `llm.js`(리뷰 생성, 성공/폴백 분기) → `postSessionToServer`/`postTodayCumulativeReviewToServer`(전송) → `server/routes/sessions.js`, `today-reviews.js`(수신·저장).
현재 **각 단계는 단위 테스트가 있지만, 이 전체가 한 번에 맞물려 동작하는지 확인하는 테스트가 0개**다. `chrome.*`와 `fetch`를 모킹한 통합 테스트 1~2개(성공 경로 1개, LLM 실패→폴백 경로 1개)만 추가해도 회귀 방지 효과가 크다.

### 6.2 [P0] 참여자 온보딩 → 그룹 배정 → 베이스라인 게이트
`GET /validate`(코드 확인) → `POST /`(등록, 그룹 확정) → 확장의 `isBaselinePeriod`/`isFeedbackNotificationEligible` 게이트. 그룹이 잘못 배정되면 전체 실험이 무효화되므로 supertest로 HTTP 레벨까지 검증하는 통합 테스트가 필요하다.

### 6.3 [P0] 대조군 종료 게이트 (3중 조건)
`POST /api/study-end-code/validate` → `participants.studyEndCodeVerifiedAt` 기록 → `GET /api/period-reviews`(종료+구간완결+코드검증 3중 AND). 개별 조건은 `period-reviews-query.js` 단위 테스트로 매우 잘 커버되어 있으나, **실제 두 라우트를 순서대로 호출하는 흐름**은 검증된 적 없다. 대조군에게 피드백/리뷰가 새는 것은 연구 윤리상 가장 심각한 실패 시나리오이므로 라우트 간 연계까지 한 번은 실제로 확인해야 한다.

### 6.4 [P1] 참여코드 기반 재설치 복구
`POST /recover` → `findEarliestParticipant` → 클라이언트가 기존 `anonymousId`로 재개. rate limit(15분 5회)까지 포함해 통합 테스트하면 브루트포스 방어와 정상 복구 양쪽을 한 번에 검증할 수 있다.

### 6.5 [P2] 기간 리뷰 배치 생성 (`generate-period-reviews.js`)
cron으로 실행되는 배치이므로 실패해도 사용자가 즉시 체감하지 못해 우선순위는 낮지만, 이미 389줄짜리 테스트가 있어(확인 필요: 실제 커버리지) 추가 투자 대비 효과는 낮다. 회귀만 주기적으로 확인.

## 7. 우선순위 (P0/P1/P2) 상세

### P0 — 지금 안 하면 데이터/연구 무결성이 실제로 깨질 수 있는 것

| 테스트 대상 | 이유 | 예상 실패 시나리오 | 유형 | 난이도 | 
|---|---|---|---|---|
| `sessions.js: validateSession` + 라우트 | 1차 연구 데이터 입구 | 잘못된 값이 그대로 저장되어 분석 단계에서 발견, 되돌릴 수 없음 | 단위+통합 | 낮음 |
| `participants.js` 등록 라우트 | 그룹 배정 오류 = 실험 무효화 | 코드 검증 우회/오배정, 중복 등록 시 그룹이 덮어써짐 | 통합 | 중간 |
| 대조군 종료 게이트 통합 흐름 | 연구 윤리 — 대조군 피드백 노출 금지 | 라우트 연계 지점에서 조건 하나가 빠져 리뷰가 새어나감 | 통합 | 중간 |
| `mergeDist`(팝업) vs `mergeSessionDistributions`(서버) 동치성 | 이미 같은 유형 버그가 2번 발생한 이력 | 팝업이 보여주는 숫자와 서버 리뷰 생성 근거 숫자가 갈라짐 — 참여자가 다른 값을 봄 | 단위(동치성) | 낮음 |
| `isBaselinePeriod`/`isConGroup`/`isTestGroup` 3종 중복 동치성 | 3중 정의, 어느 하나 수정 시 나머지가 안 따라올 위험 | 대조군인데 베이스라인 판정이 팝업/백그라운드에서 다르게 나옴 | 단위(동치성) | 낮음 |
| `content.js: extractVideoId/parseTitle` | 파이프라인 최초 입력 | 특정 URL 패턴에서 영상이 통째로 누락되거나 잘못 기록 | 단위 | 낮음 |
| `storage.js` 세션 큐 | 동시성 버그는 재현이 어렵고 발견이 늦음 | 빠른 연속 재생 시 영상 순서/세션 경계가 꼬임 | 단위(모킹) | 중간 |
| 시청 감지→피드백 저장 E2E 1개 | 전체 조각이 실제로 맞물리는지 확인된 적 없음 | 개별 함수는 통과해도 통합 지점에서 깨짐(예: 필드명 불일치) | 통합 | 높음 |

### P1 — 자주 실행되거나 사용자 경험에 직접 영향

| 테스트 대상 | 이유 | 난이도 |

## 8. 실제 구현 순서 제안

투자 대비 효과(적은 코드로 큰 위험을 없애는 순서)로 정렬했다.

1. **동치성 테스트부터** (반나절 이내): `isBaselinePeriod`/`isConGroup`/`isTestGroup` 3종, `mergeDist` vs `mergeSessionDistributions`. 이미 검증된 쪽을 기준(golden)으로 다른 쪽을 대조하기만 하면 되므로 새 로직 이해가 거의 필요 없다.
2. **`content.js` 순수 함수 2개**: 가장 저렴하고 가장 자주 실행되는 코드.
3. **`server/routes/sessions.js` 단위 테스트**(`validateSession`을 export해 순수 함수로 테스트) → 이어서 supertest로 라우트 통합 테스트.
4. **`server/routes/participants.js`** 동일 패턴 적용.
5. **`server/db.js: addColumn`**: 이미 사고 이력이 있어 재발 방지 효과가 큼.
6. **`youtube.js`, `video-events.js`, `popup-events.js`**: 패턴이 이미 확립돼 있어(sessions.js 작업에서 익힌 패턴 재사용) 빠르게 처리 가능.
7. **E2E 통합 테스트 1~2개** (`background.js` 전체 흐름, 대조군 게이트 흐름): 여기까지 오면 개별 함수가 이미 검증돼 있어 통합 테스트는 "배선이 맞는지"만 확인하면 되므로 비교적 수월하다.
8. **`backup-db.js` 리팩터 + 테스트**: `offsitePush`의 검증 함수를 분리해 export.
9. **나머지 P2**: 여유 있을 때.

## 9. 도입 과정에서 기록하면 좋은 지표

| 지표 | 측정 방법 | 왜 기록하나 |
|---|---|---|
| 테스트 개수(전/후) | `vitest run` 출력의 test 수, 이번 진단 기준 확장 5파일/서버 9파일 → 목표 파일 수 | 정량적 변화를 보여주는 가장 단순한 지표 |
| 파일별 커버리지(`vitest run --coverage`) | 현재 `vitest.config.mjs`에 coverage 설정 없음 — 먼저 `@vitest/coverage-v8` 추가 필요(확인 필요: 이미 devDependency에 없음, 신규 설치 필요) | "몇 %"보다 "P0로 지목한 파일들이 0%→고커버리지로 전환됐다"는 스토리가 더 설득력 있음 |
| 실제 발견한 버그 개수와 내용 | 각 테스트 작성 커밋 메시지/PR에 "이 테스트가 잡아낸 실제 동작" 한 줄씩 기록 | 이 프로젝트는 이미 "coderabbitai 리뷰로 발견"된 버그 2건을 코드 주석에 남기는 습관이 있음 — 같은 방식으로 테스트가 잡아낸 것도 기록하면 자연스럽게 이어짐 |
| 동치성 테스트가 잡아내는 drift 여부 | `mergeDist`/`isBaselinePeriod` 등 대조 테스트가 실패하는지 여부 자체가 지표 | "몇 개월간 아무도 몰랐던 값 불일치"를 찾으면 그 자체가 강력한 사례 |
| CI 자동 실행 여부 | 현재 `package.json`의 `test` 스크립트는 있으나 GitHub Actions 등 CI 워크플로 존재 여부(확인 필요 — `.github/workflows` 미확인) | "로컬에서만 통과"와 "PR마다 자동 실행"은 신뢰도가 다름 |
| 버그 수정 전/후 재현 테스트 | 버그를 고칠 때마다 그 버그를 재현하는 실패 테스트를 먼저 작성 → 수정 → 통과 | 회귀 방지 구조가 실제로 작동함을 보여주는 가장 직접적인 증거 |

먼저 확인할 것: `vitest.config.mjs`에 coverage 옵션이 없고 `package.json`에도 coverage 관련 패키지가 없다. 커버리지 수치를 스토리에 쓰려면 `@vitest/coverage-v8`(vitest 4.x와 호환) 설치와 설정이 선행돼야 한다.

## 10. 개발 경험 스토리 구조 (블로그/포트폴리오용)

### 10.1 서사 구조 제안

1. **문제 인식**: "테스트가 몇 개 있긴 한데, 정작 연구 데이터가 처음 들어오는 관문(`sessions.js`)은 한 번도 테스트된 적이 없다는 걸 발견했다." — 이 문서의 1~2절 내용 그대로 도입부로 쓸 수 있다.
2. **왜 이게 심각한가**: 학술 연구용 시스템이라 데이터를 되돌릴 수 없다는 제약 조건을 강조 — 일반 서비스라면 버그를 고치고 다음 배포를 기다리면 되지만, 여기서는 "이미 수집된 6주치 데이터가 오염되면 그걸로 끝"이라는 특수성.
3. **전략을 세운 방식**: 무작정 커버리지를 올리는 대신 "① 이미 검증된 좋은 패턴이 있으니 그걸 복제한다 ② 중복 구현된 로직부터 대조한다 ③ 실제 사고 이력이 있는 코드(`db.js`의 `addColumn`)부터 우선한다"는 3원칙으로 우선순위를 정한 과정.
4. **실제로 찾은 것**: `mergeDist`(팝업) vs `mergeSessionDistributions`(서버) 같은 중복 구현 drift 위험을 코드 리딩만으로 사전에 짚어낸 사례 — 테스트를 작성하기 전, "테스트 전략을 세우는 과정 자체"에서 이미 위험을 발견했다는 게 좋은 소재다.
5. **구현과 발견**: 실제로 테스트를 작성하면서 값이 갈라지는 지점을 찾았는지(찾았다면 그 자체가 하이라이트), 못 찾았다면 "왜 다행히 안 갈라졌는지"도 의미 있는 결과.
6. **구조화**: P0/P1/P2로 나눈 이유, 그리고 "테스트 개수를 늘리는 게 목적이 아니라 위험을 줄이는 게 목적"이라는 원칙을 어떻게 지켰는지.
7. **회고**: 1인 개발+연구자라는 제약 속에서 어떤 트레이드오프를 선택했는지(예: DOM 렌더링 테스트는 의도적으로 낮은 우선순위로 미룸).

### 10.2 자기소개서·면접에서 쓸 수 있는 압축 버전
"학술 연구용 크롬 확장을 혼자 개발하면서, 데이터가 한 번 잘못 쌓이면 되돌릴 수 없다는 제약 때문에 테스트 전략을 커버리지 숫자가 아니라 위험 기반으로 짰다. 코드를 읽다가 동일한 계산 로직이 서버와 클라이언트에 각각 구현돼 있는 걸 발견했고, 이미 같은 유형의 버그가 두 번 발생한 이력을 근거로 그 부분을 최우선 순위로 올렸다."

### 10.3 기술 블로그 문서 구조 제안
`docs/blog/` 폴더의 기존 관례(`2차테스트이전작업.md`처럼 실무 노트 톤)를 따라 아래 순서를 권장한다.

1. 왜 지금 테스트를 점검했는가(2차 테스트 전이라는 타이밍)
2. 진단 방법(코드를 읽고 테스트와 대조 — 이 문서의 1절 요약)
3. 발견 1: 서버 핵심 엔드포인트 공백 — 구체적 코드 스니펫과 함께
4. 발견 2: 3중 중복 로직과 drift 위험 — 왜 이게 반복적으로 일어나는 구조인지(모듈 경계상 import 불가라 매번 재정의)
5. 우선순위를 정한 기준(P0/P1/P2 원칙)
6. 실제 작성한 테스트에서 나온 결과(값이 갈라졌는지 여부, 코드로 예시)
7. 다음 단계(CI 연동, 커버리지 측정 도입)
