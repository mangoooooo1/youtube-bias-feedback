# 작업 구조 (5차)

`docs/blog/대조군-연구종료-리뷰열람-명세서.md`(Story 10-10 "대조군 일괄 피드백 공개" 하위 범위의 구체화)를 기준으로, 대조군 연구 종료 후 리뷰 열람 기능을 이슈 4개로 나눠 진행한다. 이 작업은 `Epic 10`/`Epic 11`처럼 번호가 매겨진 Epic에 속하지 않고, **"1차 테스트 이후 개발"**로 분류한다 — 파일럿(1차 테스트) 운영 중 발견된 후속 필요 기능이기 때문이다.

두 번째로, "오늘" 탭에 동시 노출되는 두 리뷰 카드(세션 리뷰·누적 리뷰 — Epic 11 Story 11-2, `docs/06-작업4.md`에서 도입)가 실제로는 서로 구분이 잘 안 된다는 문제가 코드·설계 검토 과정에서 발견됐다. 이를 세션-종료 트리거 기반의 **단일 누적 카드**로 재설계한다 — Story 11-2의 "2카드 유지" 결정을 대체하는 후속 작업이므로, 마찬가지로 번호가 매겨진 Epic에 속하지 않고 이 문서 안에 별도 Epic 섹션으로 정리한다.

각 이슈는 `docs/blog/이슈-초안-대조군-연구종료-리뷰열람.md`에 `.github/ISSUE_TEMPLATE/feat.md` 양식으로 전체 초안이 작성돼 있다. 이 문서는 실제 이슈 본문을 반복하지 않고, 착수 순서·의존관계·설계 결정 요약만 추적한다.

## Epic: 1차 테스트 이후 개발

- 설명: 대조군(CON)은 개입 기간 중 시청 현황 요약(`screenControlHome`)만 보고 실제 AI 피드백을 받지 못한다. IRB 신청서 §11(2)다), §11(3)에 "연구 종료 후 6주간 누적 시청 기록 분석·피드백을 일괄 제공한다"고 서약된 내용을 구현한다(Story 10-10 소속, `docs/05-작업3.md`).
- 진행 현황: **이슈 1·2 완료**. 이슈 3~4는 미착수(이슈 3 착수 준비 중).
- 착수 순서: 이슈 1 → 이슈 2 → 이슈 3 (직렬 의존). 이슈 4는 독립적으로 병행 가능하나, 이슈 3의 `buildWeeksData` 폴백과 함께 있어야 "재설치 후 6주 리뷰 정상 표시" 시나리오가 완결된다.
- 공통 선행 조건(모든 이슈 착수 전 확인 필요):
  - **IRB 승인 범위 확인**: 대조군 `period_reviews` 사전 생성(이슈 1)이 "언제 처리되는가"까지 IRB 승인 범위에 포함되는지 문면 확인 — **완료(승인 범위 확인됨)**.
  - **배포 전 기존 중복 데이터 점검**: 이 기능 배포 이전에 이미 같은 참여코드로 재설치가 발생해 `participants`에 중복 행이 쌓여 있는지 확인(이슈 4) — 미착수.
  - **Dependencies(Story 10-10 원본과 동일)**: Story 10-8(베이스라인·타임라인 상수, 완료됨) 필요. Story 10-9(설문 문항 확정)는 이 작업 범위와 무관 — 설문 배너는 Story 10-10의 별도 하위 작업.
- 관련 명세서: `docs/blog/대조군-연구종료-리뷰열람-명세서.md`
- 관련 문서: `docs/05-작업3.md` Story 10-10, `docs/06-작업4.md` Story 11-1(`period_reviews` 원본 설계)

### 이슈 1: [서버] 대조군 `period_reviews` 사전 생성 활성화

- 설명: `generate-period-reviews.js`의 `ELIGIBLE_GROUPS`가 지금 `["EXP","TEST-EXP"]`로 대조군을 명시적으로 제외하고 있다. 이를 확장해 대조군도 실험군과 동일한 주기·동일한 파이프라인으로 `period_reviews`가 조용히(비공개로) 쌓이게 한다. 연구 종료 시점에 별도로 소급·일괄 생성하는 로직은 만들지 않는다.
- Priority: High / Owner: BE
- Dependencies: 없음 — 가장 먼저 착수
- 상태: **완료**

#### 설계 결정 (배경)

- **사전 생성 vs 소급 생성 — 사전 생성으로 확정(사용자 결정)**: 기존 cron 인프라를 100% 재사용(배열 수정 1줄)하고, 연구 종료일에 전원(EXP+CON)의 밀린 기간이 한꺼번에 몰리는 부하를 피할 수 있다. `period_reviews` 스키마는 애초에 "그룹 무관하게 일반적으로 설계"돼 있어(기간-리뷰-생성-명세서.md 10절) 설계 의도와도 맞는다.

- 프롬프트·가드레일·fallback 로직(`server/pipeline/period-review-llm.js`) 자체는 변경하지 않는다 — 대상 그룹만 확장.

### 이슈 4: [클라이언트+서버] 참여코드 기반 재설치 복구

- 설명: `anonymousId`가 로컬(`chrome.storage.local`)에만 생성돼, 확장 재설치 시 새 참여자로 취급된다. 실험군에게도 문제지만 대조군에게는 특히 치명적이다 — 재설치하면 6주 누적 리뷰를 영영 못 받는 형태로 IRB 서약("일괄 제공")이 깨진다. 참여코드로 "이전에 설치한 적이 있는 [코드]님이 맞습니까?" 확인 후, 맞으면 기존 `anonymousId`/`installDate`를 복구한다.
- Priority: Medium / Owner: FE + BE
- Dependencies: 없음(독립 개발 가능). 이슈 3의 `buildWeeksData` 폴백과 함께 있어야 "재설치 후 6주 리뷰 정상 표시"까지 엔드투엔드 검증됨. 파일럿(1차 테스트) 종료 전 완료 권장.
- 상태: 미착수

#### 설계 결정 (배경)

- **참여코드를 사실상의 인증 수단으로 재사용**: 발급 명단(`issued_codes`)으로 온보딩 자체를 이미 통제하고 있으므로, 복구 시 같은 코드를 다시 요구하는 것은 기존 보안 모델과 일관된다. 별도의 강한 인증을 새로 설계하지 않는다.
- **`/recover`가 `installDate ASC` 첫 행을 반환**: 이 기능 배포 전 같은 참여코드로 이미 여러 번 재설치가 일어났을 가능성을 배제할 수 없다 — "가장 먼저 등록된" 행이 원래 베이스라인 시작일을 담고 있을 가능성이 가장 높다는 실용적 절충이다. 완전한 해법은 아니므로 배포 전 데이터 점검(Epic 공통 선행 조건)이 필요하다.
- **로컬 `chrome.storage.local.sessions`는 복구 범위 밖**: 서버 쪽 `anonymousId`/`installDate`/`period_reviews`는 복구되지만, 실험군의 "오늘"·진행 중 주차 화면이 의존하는 로컬 세션 캐시는 애초에 서버에 그 형태로 보관돼 있지 않아 복구 불가 — 대조군 6주 리뷰 화면은 이슈 3의 폴백 덕분에 이 한계의 영향을 받지 않는다.

### 이슈 1: [클라이언트] 세션-종료 트리거를 오늘 누적 계산으로 통합 (카드 2개 → 1개)

- 설명: `background.js`의 세션-종료 트리거(10분 비활동)가 지금은 그 세션 하나만 분석해 `buildPrompt`/`PROMPT_VERSION`으로 리뷰를 생성하는데, 이를 `aggregateTodayCumulative`(이미 존재하는 오늘 누적 병합 로직) 기반 계산으로 교체한다. 세션이 끝날 때마다 "오늘 지금까지 전체"를 재계산해 같은 카드가 갱신되며, 프론트도 "가장 최근 시청" + "오늘 하루 돌아보기" 두 `vlReview()` 호출을 카드 1개로 합친다.
- Priority: High / Owner: FE
- Dependencies: 없음 — 가장 먼저 착수
- 상태: 미착수

#### 설계 결정 (배경)

- **통합 vs 게이팅(세션 수 조건부 노출) vs 세그먼트 토글 — 통합으로 확정(사용자 결정)**: 세션 수에 따라 누적 카드 노출 여부를 조건화하는 방안(세션 2개 이상만 노출)과, 하나의 카드 안에 "최근/오늘 전체" 토글을 두는 방안도 검토했으나, 세션 단위 격리 관찰치보다 **하루 동안의 누적적 변화가 연구의 핵심 관심사**라는 점이 확인되어(사용자 결정) 애초에 카드를 하나로 합치는 방향으로 수렴했다.
- **확인(블러) 정책 — 갱신될 때마다 다시 블러(사용자 결정)**: 오늘 처음 볼 때만 블러를 씌우는 방안도 검토했으나, 세션이 끝나 카드 내용이 갱신될 때마다 다시 블러 처리해 매 갱신에 대해서도 확인 신호를 남기기로 했다. 기존 `locked`/`feedbackViewedAt`/`feedbackConfirmedAt` 메커니즘을 그대로 재사용할 수 있다(세션마다 새 `sessionId`가 생겨 자연히 구분됨).
- **세션 단독 프롬프트 경로 폐기**: `buildPrompt`/`PROMPT_VERSION`("viewlens-mirror-v1.0")은 오늘 탭에서 더 이상 쓰이지 않고 `buildTodayCumulativePrompt` 계열로 통일한다. 통합 전/후 데이터를 구분할 수 있도록 새 프롬프트 버전 문자열 발급을 제안한다(예: `viewlens-unified-mirror-v1.0`).
- **⚠️ 연구 데이터 재정의**: `sessions.review`의 의미가 "그 세션 하나에 대한 격리된 관찰치" → "세션 경계마다의 누적 스냅샷 시계열"로 바뀐다. 의도된 변경이나(위 결정 참고), 세션을 독립 관찰치로 다루는 기존 분석 스크립트가 있다면 영향을 받는다.
